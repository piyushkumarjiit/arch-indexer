# arch-indexer

`arch-indexer` reads a source repository and produces accurate, human-readable documentation for it:

- a **technical design document** covering architecture, components, control and data flows, data model, interfaces, security and deployment;
- a **user guide** that explains, per user role, what the system does and how to use it.

Every technical claim in the generated documents is traceable to the code through `file:line` references. A deterministic citation checker verifies those references before the documents are accepted.

## How it works

1. **Index (no AI).** Detects the languages in the target repository, runs `arch-indexer toolchain ensure` automatically (unless `--offline` is passed) to install any missing pinned indexers, and builds a local index of symbols, definitions and references. It currently targets Python, TypeScript and Java/Maven, plus infrastructure files such as Dockerfiles, Compose/Kubernetes manifests, Spring/env config bindings, shell scripts, Terraform and SQL schema migrations. A precise SCIP indexer is used when the project can be resolved; otherwise a no-build parser is used as a fallback.
2. **Detect changes (no AI).** Compares the repository with the previous run and reports only what changed, so an unchanged repository costs nothing to re-check.
3. **Graph and visualise (no AI).** Exports a control- and data-flow graph, generates the Mermaid diagrams used in the design document, and builds an offline HTML viewer for exploring flows from entry points to data stores, LLM APIs and external sinks.
4. **Write (AI workers, bounded).** Writers read the index through a local query tool, draft only the sections affected by a change, and cite the code for every claim. Plain-language descriptions of parts, groups, boundaries and key flows are planned and linted by the same pipeline.
5. **Assemble and verify.** Assembly runs with no AI: it merges the drafts, embeds the diagrams and runs the citation and diagram checks. Independent judge models then verify the claims against the cited code.

Querying, graphing, assembly and validation run offline; indexing runs toolchain ensure automatically unless `--offline` is passed, `toolchain prime` is the explicit online step that prepares a Java repository's local Maven repository, and `index --maven-online` is the opt-in that lets Maven fetch during indexing.

## Install and usage

```bash
pip install -e .   # add "[dev]" for pytest, pytest-xdist and ruff; add "[browser]" for the Playwright Chromium test

# Toolchain management
arch-indexer toolchain status --repo /path/to/repo
arch-indexer toolchain ensure --repo /path/to/repo   # install missing pinned indexers (also run automatically by index without --offline)
arch-indexer toolchain prime --repo /path/to/repo    # online: install Maven dependencies so index --offline can build Java

# Index a repository (Tier 1 SCIP, Tier 2 tree-sitter fallback; tests are indexed for references
# but excluded from modules, packets, entrypoints and diagrams unless --include-tests is passed)
arch-indexer index /path/to/repo [--include-tests] [--strict-tier1-any] [--max-parallel-units N] [--viewer v2|v1] [--maven-arg=<arg>]... [--maven-online] [--maven-reactor]

# Read-only queries over the local index (offline, deterministic)
arch-indexer query /path/to/repo def <symbol> [--json]
arch-indexer query /path/to/repo refs <symbol> [--limit 100] [--include-tests] [--json]
arch-indexer query /path/to/repo file-symbols <rel-path> [--json]
arch-indexer query /path/to/repo units [--json]
arch-indexer query /path/to/repo entrypoints [--module <mod>] [--include-tests] [--json]
arch-indexer query /path/to/repo module-summary <mod> [--include-tests] [--json]
arch-indexer query /path/to/repo flow-trace <entrypoint-id> [--depth 6] [--include-tests] [--json]

# Join live-production traces onto the v2 bundle (span files offline; Jaeger read-only;
# writes docs/arch/runtime-overlay.v1.{json,js})
arch-indexer trace ingest /path/to/repo (--otlp-file <path> | --collector-file <path> | --jaeger <url> --service <name>) \
  [--lookback 1h] [--limit 200] [--path-prefix-map SRC=DST]... [--docs-dir docs] [--cache-dir <dir>]

# Optional read-only localhost viewer server, with optional Jaeger polling
arch-indexer serve /path/to/repo [--docs-dir docs] [--host 127.0.0.1] [--port 8765] \
  [--jaeger <url> --service <name>] [--lookback 1h] [--limit 200] [--poll-interval 15] \
  [--path-prefix-map SRC=DST]... [--cache-dir <dir>]

# Validation gates (offline; exits 0 on clean, 3 on validation failure)
arch-indexer check-citations /path/to/repo [--docs-dir docs] [--file <path>] [--format text|json]
arch-indexer check-mermaid /path/to/repo [--docs-dir docs] [--format text|json]

# Bounded worker planning (offline; --by defaults to parts when the bundle holds 2+ parts)
arch-indexer plan /path/to/repo [--by parts|modules] [--max-lines-per-worker 15000] \
  [--max-symbols-per-worker 800] [--max-sections-per-worker 3]

# Deterministic assembly of worker drafts (offline; exits 3 and keeps the drafts on failure)
arch-indexer assemble /path/to/repo --drafts-dir docs/.drafts [--docs-dir docs] \
  [--diagrams <json>] [--remove-slice <packet_id>]...

# Plain-language descriptions (offline; check exits 3 on invalid content and writes descriptions.js)
arch-indexer describe plan /path/to/repo [--top-flows 10] [--docs-dir docs]
arch-indexer describe check /path/to/repo [--input docs/arch/descriptions.json] [--format text|json]

# Cross-model claim verification (offline; gate exits 3 on a failed gate and 1 on invalid input)
arch-indexer verify-claims plan /path/to/repo [--docs-dir docs] [--descriptions <path>]
arch-indexer verify-claims gate /path/to/repo --verdicts <jsonl> [--verdicts <jsonl>]... \
  --writer-model <id> [--judge-model <id>] [--judges 1] [--max-partial 0.05] [--format text|json]
```

### Validation Gates

- **`check-citations`**: Parses footnote references (``[^n]: `file_path:line` — `symbol` ``) in `docs/DESIGN.md` and `docs/USER_GUIDE.md` (or specific files passed with `--file`). Verifies that each cited file exists within the repository, line numbers are in range, and symbols match definitions in `index.db` or literal line tokens. Detects dangling footnote references, duplicate definitions, format errors, drifted symbols (`SYMBOL_DRIFTED_TO:<line>`), and, in `docs/DESIGN.md`, technical sections that carry body text but no citations (`UNCITED_SECTION`). In both documents a required `SECTION` block — one without the `:exempt` flag — whose content is only headings, comments, fenced code or footnote definitions fails with `EMPTY_SECTION`.
- **`check-mermaid`**: Pure-Python static validator for fenced ```` ```mermaid ```` diagram blocks in documentation. Verifies diagram declaration headers (`flowchart`, `graph`, `sequenceDiagram`, `classDiagram`, `erDiagram`, `stateDiagram-v2`), non-empty bodies, balanced `subgraph`/`end` blocks and delimiters, balanced `sequenceDiagram` blocks (`loop`, `alt`/`else`, `opt`, `par`/`and`, `rect`, `critical`/`option`, `break`, `box` each closed by `end`), node ID characters, edge arrows, and `AUTO-DIAGRAM` markers. When `docs/graph.json` exists, each `AUTO-DIAGRAM` block must exactly equal the diagram regenerated from that graph, and every deterministic diagram the graph produces must have a block in `docs/DESIGN.md`; edits or missing blocks fail with exit `3`.
- **`describe check`**: Validates `docs/arch/descriptions.json` against `docs/arch/overview.json` and the indexed code, then writes its viewer twin `docs/arch/descriptions.js` on success. It enforces the bounded summary/details lengths, fresh-or-stale status, a non-empty in-repo citation inside the described entity's own files, span hashes for fresh entries, the flow title/step contract, and the plain-language jargon lint (with `[describe] allow_jargon` exemptions), and rejects keys for files, endpoints and symbols. Errors fail with exit `3`; see [section 8.4 of the spec](docs/SPEC.md).
- **`verify-claims gate`**: Gates `docs/DESIGN.md`, `docs/USER_GUIDE.md` and the descriptions against independent judge verdicts from one or more JSONL files. It refuses a judge equal to the writer model, requires the requested number of distinct judges and a verdict for every planned claim, and fails with exit `3` on any claim contradicted or on a partial-plus-bad-citation rate above `--max-partial`. See [section 8.5 of the spec](docs/SPEC.md).

### Indexing

`index` discovers Python, TypeScript/JavaScript and Java/Maven units plus infrastructure units with a pure-Python scanner, writes `<cache>/repos/<id>/index.db`, and prints a summary line followed by one tier line per unit, then a delta summary whose wording always agrees with the exit code, plus impacted- and missing-section counts when any remain (see [section 7.2 of the spec](docs/SPEC.md)). Re-runs are incremental: an unchanged unit is reused from `index.db` instead of being re-parsed, a changed unit re-parses only its changed files unless its build manifest changed or the unit is Tier 1 (SCIP indexes a whole unit at a time), and files whose references point at a removed or newly added symbol are re-indexed too, so a one-file edit no longer rebuilds the whole database. `--force-full` still rebuilds everything, and an `index.db` written by an older schema major is rebuilt once automatically. `--max-parallel-units N` runs up to `N` planned full units' Tier 1 indexing concurrently (default `1`; each concurrent unit holds its own Node/JVM heap, so raise it only within the host's RAM budget) and writes the resulting rows serially in deterministic unit order, so parallel and serial runs produce identical rows and `graph.json` (see [section 4.6 of the spec](docs/SPEC.md)). Language units use their pinned Tier 1 SCIP indexer when available (installed automatically by `toolchain ensure` unless `--offline` is passed; add `--fetch-runtime` to also fetch the pinned portable JDK/Maven) and its runtime is available; otherwise they use the Tier 2 `tree-sitter` parser, while infrastructure units always use the pure-Python scanner. Every file row records its `tier` (`scip` or `tree-sitter`) and, for a Tier 2 fallback, the `fallback_reason`; `query <repo> units` reports the same per unit, including the captured failure message, and `index` prints a loud warning when every file in a unit falls back. The summary splits unresolved references into external third-party symbols and in-repo symbols (the only class that signals a defect) while keeping `total_unresolved_refs` as the backward-compatible total; `master-index.json` carries the same `unresolved_external_refs`/`unresolved_in_repo_refs` split. Its file, symbol, reference, entrypoint, infra and unresolved counts are scoped exactly like `master-index.json` (test code excluded unless `--include-tests`), with the number of excluded test files printed beside them. The cache defaults to `${XDG_CACHE_HOME:-~/.cache}/arch-indexer`; set `ARCH_INDEXER_CACHE` or pass `--cache-dir` to override it.

Test files are indexed so `def` and `refs` stay traceable, but they are not architecture: unless `--include-tests` is passed, they produce no modules, entrypoint nodes, diagram domains, `master-index.json` modules or totals, work packets or delta entries. [Section 6.1 of the spec](docs/SPEC.md) lists the exact path patterns.

Each run also writes `<cache>/repos/<id>/master-index.json`, the compact module, file, symbol, entrypoint and unresolved-reference summary that `plan` and the workers read. It then snapshots the indexed tree to `<cache>/repos/<id>/state.json` (file and symbol signatures, the module-to-section map and the hashes of generated diagram blocks; see [section 5.1 of the spec](docs/SPEC.md)) and diffs the snapshot against the previous run into `index-delta.json` and `impacted-sections.json` next to `index.db`:

- **First run** (no `state.json`, or `--force-full`): every non-test file is reported as added, every existing section is impacted (a canonical document with no sections contributes its full canonical outline), and `index` exits `2` (`DELTA_DETECTED`).
- **Unchanged repository with up-to-date documents**: the delta is empty and `index` exits `0` (`NO_CHANGES`), so no workers are needed.
- **Changes**: added/modified/deleted non-test files and symbols are reported. Deleted files are purged from every `index.db` table and every section citing them is impacted. Sections covering a module with new files or symbols are impacted through the stored module-to-section map, newly added modules without a covering section are listed under `missing_sections`, and an `AUTO-DIAGRAM` block edited since the last index marks its section impacted even when the source tree is unchanged.
- **Line-shift-only changes**: when the only difference is moved symbols (same body, visibility and decorators, unchanged file content signature, new line numbers; see [section 5.4 of the spec](docs/SPEC.md)), `index --auto-relocate-citations` rewrites the shifted `file:line` footnotes in `docs/DESIGN.md` and `docs/USER_GUIDE.md`, including footnotes that cite a call site rather than a definition, re-runs `check-citations` and updates `state.json`. Because diagram node ids embed source line numbers, the same run also regenerates the tool-generated `AUTO-DIAGRAM` blocks, so a pure line shift leaves both gates green. It exits `0` when no section remains impacted, `2` when a relocated document still has an impacted section (an edited `AUTO-DIAGRAM` block or a missing canonical section), and `3` (`VALIDATION_FAILED`) when citations still fail.

A required section whose body is still empty is impacted with the `empty_section` reason on every run, so an unchanged repository whose documents are not yet complete keeps exiting `2` until those sections are written.

Sections are read from existing documents through `<!-- SECTION:<id>:START -->`/`<!-- SECTION:<id>:END -->` markers, or from every `##` heading when a document has no markers; a start marker may carry the `:exempt` flag defined in [section 9.2 of the spec](docs/SPEC.md).

**Module identity.** Modules come from real structure, not one fixed package level: a Maven reactor module plus the package below it, otherwise the package path with source roots and a shared Python container package stripped, and any module larger than the planner's per-worker budget splits recursively into its subpackages. [Section 6.1 of the spec](docs/SPEC.md) owns the derivation. Override it with `arch-indexer index --module-depth N` (fixed depth, no adaptive split) or a `.arch-indexer.toml` at the repository root:

```toml
[modules]
depth = 2            # same as --module-depth (the flag wins)

[modules.map]
"services/billing" = "billing"   # path prefix -> module name (longest prefix wins)

[parts."billing"]
paths = ["services/billing/**"]   # path globs; a module joins the part matching most of its files

[viewer]
editor_url = "vscode://file/{abs_path}:{line}"   # {abs_path}, {file} and {line} are substituted

[describe]
allow_jargon = ["dto", "middleware"]   # terms exempt from the plain-language jargon lint
```

Parts are derived deterministically from deployable roots (`service`, `ui`, `worker`, `scripts`, `library` and `infra`), and an explicit `[parts."<name>"]` table wins over that derivation so a repository can name its own; `[viewer] editor_url` is the template the viewer uses to link evidence rows to an editor; its scheme must be one of the accepted schemes listed in [section 6.3 of the spec](docs/SPEC.md), and an unsupported scheme fails config load and never renders as a link. `[describe] allow_jargon` exempts repository vocabulary from the `describe check` jargon lint.

`plan` marks a packet `"over_budget": true` and warns on stderr when a module cannot be split further (see [section 9.2 of the spec](docs/SPEC.md)).

Boundary and entrypoint classification is data-driven as well: the built-in rules live in `src/arch_indexer/rules/*.toml`, and the same `.arch-indexer.toml` can replace a rule by `id` or add repository rules through `[[rule]]` tables or the `[boundaries."<package>"]` shorthand. `[graph] dispatch_fanout_cap` (default `5`) bounds how many implementing methods one interface call may expand to; `.arch-indexer.proposals.toml` is never loaded automatically.

`--docs-dir` selects where the generated artifacts (`docs/graph.json`, `docs/flow-viewer.html`, the `docs/arch/` summary-plus-detail bundle and `docs/arch/dependencies.json`) are written, and where documents are read from and citations relocated. `--offline --strict-tier1` exits `4` only when a required Tier 1 indexer or its runtime is not available; runtime failures such as OOM, timeout, missing `node_modules`, unresolved Maven artifacts or a failed build fall back to Tier 2 with the `fallback_reason` recorded. `--strict-tier1` without `--offline` also falls back to Tier 2. `--strict-tier1-any` is the stricter form: online or offline, it exits `4` when any unit whose language has a Tier 1 indexer falls back for any reason, and it resolves every unit before touching the stored index, so an existing `index.db` is left intact.

Maven builds run offline (`-o`) by default so a missing private artifact falls back instead of stalling on the network. When a cold or partial local repository defeats that, `--maven-online` drops `-o` and repeatable `--maven-arg=<arg>` forwards extra arguments to Maven (for example `--maven-arg=-Dmaven.repo.local=/path/.m2 --maven-arg=--also-make`); write `--maven-arg=<arg>` with `=` when the argument itself starts with `-`. Because each Java unit builds one module directory outside reactor context (unless `--maven-reactor` covers it), dependencies on sibling modules must already be in the local repository: prime it once, online, with `arch-indexer toolchain prime --repo <repo>` (the repository's resolved Maven runs `-B -DskipTests clean install`, which also fetches `maven-clean-plugin`), or run the repository's own Maven with `mvn -q -DskipTests install`, and use `--maven-online` or a primed `--maven-arg=-Dmaven.repo.local=...` when the default `~/.m2` is not it. If an offline run still fails only because `maven-clean-plugin` cannot be resolved, `clean` is retried once without it after removing `target/classes` (and `target/test-classes` with `--include-tests`); a failed retry records `maven_clean_plugin_offline`.

Units run `clean compile -DskipTests`, so `src/test` sources are not compiled. With `--include-tests` the goal becomes `clean test-compile -DskipTests` and test files can reach Tier 1; the tier consequence is that a module whose test sources do not compile (for example a test-scoped dependency missing from the offline repository) fails as a whole and falls back to Tier 2, main sources included. Without `--include-tests` nothing changes.

Each module normally costs its own Maven and scip-java JVM start-up. `--maven-reactor` is an opt-in alternative for multi-module repositories: one scip-java run at the root `pom.xml` (with the same `--maven-arg`, `--maven-online` and test-compile settings) whose output is split per module. A module is only read from that output when its files actually appear in it; a failed run, an exit 0 without a `.scip` (which scip-java does for some `packaging=pom` aggregators), or modules missing from the output are reported on stderr and indexed with the per-module run instead, so nothing silently produces no index. Without a multi-module root `pom.xml` the flag has no effect beyond a stderr note.

`ensure` needs host `node`/`npm` for the Python and TypeScript indexers, and host `java` (plus `mvn` for Maven builds) for `scip-java`. A missing runtime with no usable portable alternative is reported as a warning; `index` then either falls back to Tier 2 tree-sitter indexing for that language or, under `--offline --strict-tier1`, exits `4`. For Java repos, pass `--fetch-runtime` to download the pinned Eclipse Temurin JDK 17 into `<cache>/runtimes/` when host `java` is missing or older than the minimum, and Apache Maven 3.9 as well when the repo contains a `pom.xml` and host `mvn` is missing or unusable; each archive's SHA-256 is verified before safe extraction. A host `mvn` below the repository's `RequireMavenVersion` range (`pom.xml`) is rejected as unusable, and `toolchain status` names the mismatch (`repo requires [3.9.0,4.0.0)`) instead of reporting the host as OK; `--fetch-runtime` then fetches and prefers the pinned portable Maven when the pinned 3.9.16 itself satisfies that range. A host that satisfies the repository but is below the pinned Maven version stays usable and is only noted in `toolchain status`. Host runtimes are still preferred when they are usable (see Disagreement 1 in [docs/SPEC.md](docs/SPEC.md)). The flag governs downloads only: a runtime already downloaded and verified is reused by later `ensure` runs without it, and `ensure` prints one line per portable runtime saying whether it was downloaded or reused.

```bash
arch-indexer toolchain ensure --repo /path/to/java/repo --fetch-runtime
```

### Planning

`arch-indexer plan <repo> [--by parts|modules] [--max-lines-per-worker 15000] [--max-symbols-per-worker 800] [--max-sections-per-worker 3]` partitions the impacted documentation sections and oversized modules reported by the last `index` run into bounded, disjoint work packets written to `<cache>/repos/<id>/work-plan.json`. It reads `impacted-sections.json`, `master-index.json` and the `docs/graph.json` graph, and uses the `docs/arch/overview.json` parts when they exist; it exits `1` when a required input is missing. `--by` selects the planning axis: `parts` is the default whenever the bundle holds at least two derived parts, and `modules` remains available (and is the fallback for smaller repositories); `--by parts` without part data exits `1`. Parts-first planning shards `DESIGN.md` §2 into one packet per part and carries the part's verified descriptions into the packet; `work-plan.json` records the chosen `axis`, and each packet may add `assigned_parts` and `verified_descriptions` to the common fields (target document, canonical section identifiers, assigned modules, delta slice, pre-rendered diagram identifiers and a unique draft path under the run's docs directory, `docs/.drafts/<packet_id>.md` by default). On an incremental run an empty delta slice is not dispatched, so a one-module edit does not produce a worker per untouched module slice. Structural work (a missing or empty section, or an edited `AUTO-DIAGRAM` block) is exempt because it needs a worker even when the source tree has no delta; first runs keep every packet and a fully up-to-date run emits none.

### Assembly

`assemble` turns worker drafts into the canonical documents. It starts a missing `docs/DESIGN.md` or `docs/USER_GUIDE.md` from the packaged skeleton, then replaces only the per-packet slices this run drafted, leaving sibling slices and untouched sections in place, renumbers footnotes globally, fills diagram slots from `--diagrams`, and runs both validation gates. Because a document started from the skeleton is mostly empty, that citation gate tolerates empty sections; the following `index` run re-impacts them with `empty_section` instead. When `docs/graph.json` exists, `assemble` then rewrites every `AUTO-DIAGRAM` slot in `docs/DESIGN.md` to that graph's deterministic diagrams: graph output takes precedence over `--diagrams` (so the flag is optional), missing `flow-<domain>` slots are inserted and slots the graph does not produce are dropped. Consumed drafts are deleted only when every gate passes; a failed gate exits `3` and keeps them. `--remove-slice` retires the slice of a packet that no longer exists (a deleted or re-sharded module). `--drafts-dir`, `--docs-dir` and `--diagrams` paths resolve against the target repository, never the current directory, and the drafts directory must live inside it, but must not be the repository root, equal the docs directory, or contain it. Running `assemble` before any drafts exist is a bootstrap step: it creates the in-repo drafts directory, prints the draft-packet contract and the section ids still without body text, and exits `0`. A missing `docs/DESIGN.md` or `docs/USER_GUIDE.md` is skipped consistently by both gates rather than failing them, and `assemble` reports that skip once. The draft file format is specified in [docs/SPEC.md](docs/SPEC.md) §9.2.

### Graph and flow viewer

`arch-indexer index` exports the deterministic SPEC 6.1 graph to `docs/graph.json`, writes `docs/flow-viewer.html` and the `docs/arch/` summary-plus-detail bundle from the same payload, and writes the package dependency catalog to `docs/arch/dependencies.json`. The graph is built only from `index.db` plus the repository name, git HEAD, the resolved test scope and the repository's `.arch-indexer.toml` overrides (a small set of files is re-read for default-argument resource values), with sorted modules, nodes, edges, data stores, external sinks, sidecars and shared resources, so repeated runs over an unchanged repository produce byte-identical files. Each module carries its majority `tier` plus a `tier_mix` of per-tier file counts, and `tier_summary` reports `total_files` and `excluded_test_files` so its counts agree with the modules and tier table. The indexer records entrypoint auth guards, indexing tiers, data-store/external-sink evidence and the matched `rule_id`, and counts unresolved references. The graph also carries a `files[]` entry for every in-scope file (module, language, tier, line count, infra flag and symbols), a `confidence` on every node and edge, `registers` edges for callbacks passed as arguments, and `boots` edges from an application start to the scheduled, event, queue and runner entries it launches; code with no function owner gets a synthetic `<module>` or block symbol so its calls and registrations stay attached. `graph.json` is the single input for Mermaid generation and drives the `docs/arch/` bundle, which adds the derived parts, symbol docstrings and per-part chunk split from the same index.

Cross-component connectivity is part of that payload: `implements` edges connect in-repo types to their interfaces, a call to an in-repo interface expands through polymorphic dispatch up to the fan-out cap, frontend API callers link to the backend routes they call, and the `resources` array records shared `res:<kind>:<value>` artifacts with the writers and readers found in different modules or entry roots. Infrastructure services that are not the repository's own build become `sidecar` nodes (`svc:*`) with `http_request` edges, and the `sidecars` array keeps the image and the config site that binds each one. The dependency catalog groups imports, unresolved references and build manifests into sorted packages with capped sites and the matched boundary rule; [section 6.1 of the spec](docs/SPEC.md) owns the graph schema and [section 6.4](docs/SPEC.md) the catalog.

The same payload generates the Mermaid diagrams. When the bundle holds two or more derived parts (parts-first docs mode), `module-overview` is a `flowchart LR` of parts plus data stores and external sinks (child modules appear in each part label) and each part gets one boundary-centred `flow-<part-slug>` diagram with at most its top three flows; otherwise the diagrams are `module-overview` over modules and one `flow-<domain>` diagram per entrypoint domain (`flowchart TD` from entrypoints through services to data stores and sinks). Generation is deterministic and respects the generator's fixed node/edge budgets (35 nodes and 60 edges); when a graph exceeds a budget, service nodes are aggregated to their modules (keeping the dominant module) and entrypoints are capped so call edges always remain, with a note pointing at `docs/flow-viewer.html`. [Section 6.2 of the spec](docs/SPEC.md) defines the exact collapse and truncation rules. `check-mermaid` regenerates each `AUTO-DIAGRAM` block from `docs/graph.json` (using the same parts-first mode) and fails on any manual edit or missing block.

The viewer is written to `docs/flow-viewer.html` and by default is the v2 React Flow + ELKjs app: the pre-built assets ship in the package (rebuild them with `make viewer`), the page embeds `docs/arch/overview.json` and loads one JSONP detail chunk per part from `docs/arch/chunks/`, so it opens over `file://` with no server and no network while each file stays small. When `describe check` has emitted the real `docs/arch/descriptions.js`, nodes and the inspector show the plain-language summary (a `stale` badge and dimmed card when `index` marked the entry stale), and the flow banner shows the flow title and per-step narration. It drills from the overview (parts and boundaries, with the summary panel) into a part (the `Used by` / `Inside` / `Uses` bands drawn from the real partition bounds), then group, file and symbol (a call tree to depth 3), folding anything past the 300-node cap of a view into a `+N` node whose items the inspector lists as jump links. One merged edge is drawn per node pair and filtered by the control, data and integration layers (runtime joins once an overlay exists), with the per-kind breakdown in the edge inspector; flows play from a banner with `Follow step` on by default, `changed`/`new` badges come from the delta, and the Tier-2 warning collapses to a pill (its module chips capped at 12 plus `+N more`) but never disappears. `--viewer v1` writes the older self-contained vanilla-JS viewer (`arch_indexer.viewer.render_viewer`) instead, which embeds `graph` and exposes a "Load `graph.json`" file picker so any standalone graph can be opened without a web server; `index` falls back to it when the pre-built v2 assets are missing. See [section 6.3 of the spec](docs/SPEC.md) for the full viewer contract.

### Runtime overlay and live viewer

`arch-indexer trace ingest` joins runtime spans — an OTLP JSON or protobuf file, an OTel Collector file-exporter JSON/JSONL file, or a read-only Jaeger `/api/v3/traces` query — onto the `docs/arch/` bundle written by `index`, and writes `docs/arch/runtime-overlay.v1.json` plus its `window.__ARCH_RUNTIME__` sidecar. Spans match by ranked tier (code location or exception frame, normalised HTTP route, database/messaging peer, then service name); `--path-prefix-map SRC=DST` maps instrumented container paths onto repository paths. A run where fewer than 10% of spans match (including an empty input) exits `3` and prints the top unmatched span names. The overlay never changes `graph.json`, the static `docs/arch/` bundle or `flow-viewer.html`, and a re-index resets the sidecar to a `null` stub when no overlay JSON exists.

The v2 viewer loads the overlay through **Load Runtime** (a file picker) or from the `runtime-overlay.v1.js` sidecar, and on an HTTP-served page **Live poll** re-reads `docs/arch/runtime-overlay.v1.json` every 5 seconds. With an overlay loaded, the Runtime layer colours nodes by p95 latency and errors, shows the match tier and error count, draws runtime-only edges as dashed drift, adds exception types and frames to the inspector, and offers trace replay. `arch-indexer serve` is the optional Decision D5 server for live debugging: a read-only (GET/HEAD) localhost server for the docs directory, by default at `http://127.0.0.1:8765/flow-viewer.html`, which can poll Jaeger in memory with `--jaeger`/`--service` and serve the live overlay with `Cache-Control: no-store`. [Section 6.3 of the spec](docs/SPEC.md) owns the overlay and server contract.

### Querying

`query` opens `<cache>/repos/<id>/index.db` read-only and prints deterministic, line-oriented rows with `path:line`; add `--json` for structured output. The cache location follows the same rules as `index`, so pass the same `--cache-dir` when one was used. Every command exits `1` with a clear message when the index is missing or the symbol, file, module or entrypoint is unknown.

- `def <symbol>` resolves an exact fqname, then an exact name, then a dotted suffix.
- `refs <symbol> [--limit 100] [--include-tests]` lists imports, calls and other references; the limit caps output (`--json` reports the untruncated `count` and `truncated`). A symbol that is defined in the index but has no references exits `0` with an empty result. A reference located in a test file is neither returned nor counted unless `--include-tests` is passed.
- `file-symbols <rel-path>` lists the symbols defined in one indexed file.
- `entrypoints [--module <mod>] [--include-tests]` lists detected HTTP routes, CLI commands, `__main__` blocks, Java process entrypoints (`main` including `@SpringBootApplication` classes, `CommandLineRunner`/`ApplicationRunner`; kind `process`), `@Scheduled` jobs (`scheduled`), `@KafkaListener`/`@RabbitListener`/`@JmsListener` consumers (`queue`), Spring `@EventListener`/`@TransactionalEventListener` handlers (`event`), JAX-RS `@Path` resources (`http`), gRPC service implementations (`grpc`), `ActionExecutor` implementations (`job`), HTTP entries discovered from server-scoped route literals (`http`) and frontend API callers with their numeric `id`. Each row reports the discovery `line` and the definition `symbol_line` that citations must use; text output adds `symbol_line=<n>` when it differs. See [sections 7.1 and 8.2 of the spec](docs/SPEC.md) for both fields and the citation rule.
- `units` lists every indexing unit with its file count, tier, fallback reason and the captured fallback message (truncated), which is how a silent all-Tier-2 Java fallback is diagnosed.
- `module-summary <mod> [--include-tests]` prints a module's file, symbol and entrypoint counts followed by its files, symbols and entrypoints. Both this command and `entrypoints --module` accept the `mod:<key>` id or bare module key used by `docs/graph.json`, `master-index.json` and `work-plan.json`, and a dotted package namespace such as `pkg.mod`.
- `flow-trace <entrypoint-id> [--depth 6] [--include-tests]` walks the call graph breadth-first from the entrypoint's symbol, printing the root as `0 file:line symbol` and each call as `depth file:line caller -> callee`. It follows the same cross-component edges as `graph.json`: a call to an in-repo interface expands through its `implements`/`overrides` relations (bounded by the dispatch fan-out cap), `registers` callbacks and `boots` triggers are followed, and a frontend API caller links to the backend route it calls. A `main` or CLI entrypoint roots at its synthetic module/`__main__` block; an entrypoint with no indexed enclosing symbol (for example a module-level TypeScript `fetch`/`axios` call) fails instead of guessing a root. It stops at a bounded depth and marks callees that have no definition in the index and match the known data-store or external-sink client symbols (kept in `src/arch_indexer/known_symbols.py`) as `[datastore]` or `[external-sink]`. Callees defined in the repository are always expanded, never marked. A call edge located in a test file is not followed unless `--include-tests` is passed, and a test-file entrypoint cannot start a trace.

Test files are outside the default architecture scope (see [Indexing](#indexing)); `entrypoints`, `module-summary`, `refs` and `flow-trace` include them when `--include-tests` is passed.
